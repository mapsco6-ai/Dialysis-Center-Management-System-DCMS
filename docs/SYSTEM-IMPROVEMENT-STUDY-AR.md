## 1) جرد الحالات (States) الموجودة في الـ Backend

25 enum في `schema.prisma`. لكل مجموعة: الحالات الحالية، ما يناقصها، والتحسين المطلوب.

### 1.1 المريض والجدولة

| Enum | القيم الحالية | الملاحظة / التحسين |
|---|---|---|
| `PatientStatus` | ACTIVE, INACTIVE, DECEASED, TRANSFERRED | أضف **`ON_HOLD`** (إيقاف مؤقت: سفر/دخول مستشفى) و**`TRANSPLANTED`** (زراعة كلية = خروج إيجابي). أضف حقل سبب الانتقال وتاريخه (`statusReason`, `statusChangedAt`) بدل الاكتفاء بالـ Audit. |
| `AlertSeverity` | CRITICAL, IMPORTANT, INFORMATION | جيدة. أضف حالة للتنبيه نفسه (`OPEN / ACKNOWLEDGED / RESOLVED`) ومن أقرّ به ومتى، حتى لا يبقى التنبيه ظاهراً للأبد ولا يُخفى بلا أثر. |
| `ScheduleStatus` | SCHEDULED, ARRIVED, LATE, ABSENT, CANCELLED, EXTRA, EMERGENCY | **خلط بين حالتين:** `EXTRA/EMERGENCY` هي نوع (موجودة أصلاً في `ScheduleType`) وليست حالة. افصلها. أضف `NO_SHOW_EXCUSED` (غياب بعذر) و`RESCHEDULED` مع رابط للموعد الجديد. |
| `ScheduleType` | REGULAR, EXTRA, EMERGENCY | تبقى. |
| `ShiftName` / `Weekday` | 4 ورديات / 7 أيام | ثابتة في الـ enum. الأفضل أن تصبح الورديات **بيانات** (جدول `Shift` موجود أصلاً) فلا يحتاج مركز بـ 3 ورديات أو 5 لتعديل الكود. |

### 1.2 الجلسة السريرية

`DialysisSessionStatus`: PRE_DIALYSIS → SUPPLIES_READY → WAITING_MACHINE → ASSIGNED → IN_DIALYSIS → POST_DIALYSIS → COMPLETED → DISCHARGED (+ INTERRUPTED).

- الانتقالات مُنفَّذة كدوال منفصلة (`preDialysis`, `start`, `end`, `discharge`, `interrupt`, `resume`) لكن **لا يوجد جدول انتقالات مركزي** كما في الأجهزة والصيانة والمختبر. القاعدة تتوزع داخل كل دالة.
- **التحسين:** جدول `ALLOWED_SESSION_TRANSITIONS` واحد + دالة `transitionSession()` واحدة (نفس نمط `MachinesService.transitionStatus`)، فتُسجَّل كل الانتقالات في تاريخ حالة (`SessionStatusHistory`) بمن/متى/لماذا. هذا يخدم التدقيق والمؤشرات (زمن الانتظار بين الوصول والبدء).
- أضف `CANCELLED_BEFORE_START` (إلغاء قبل البدء) و`TRANSFERRED_OUT` (نُقل لمستشفى أثناء الجلسة، مرتبط بحادثة).
- `DialysisEventType`: أضف `CRAMPS`, `BLEEDING`, `CHEST_PAIN`, `CLOTTING`، فهي أكثر مضاعفات الديلزة شيوعاً، وتُبنى عليها مؤشرات الجودة.

### 1.3 الأجهزة والصيانة والمخزون

| Enum | الملاحظة |
|---|---|
| `MachineStatus` (9 حالات) | مصممة جيداً بجدول انتقالات (`ALLOWED_GENERIC_TRANSITIONS`). **الناقص:** حالة `RETIRED` (خارج الخدمة نهائياً) وعدّاد ساعات التشغيل للصيانة الدورية. |
| `MaintenanceTicketStatus` | مصممة جيداً. أضف `CANCELLED` (بلاغ خاطئ) و**SLA**: زمن استجابة متوقع حسب `MaintenanceSeverity` مع مؤشر تأخر. |
| `StockTransferStatus` | REQUESTED→APPROVED→ISSUED→RECEIVED/REJECTED. أضف `CANCELLED` و`PARTIALLY_RECEIVED`. |
| `SupplyIssueStatus` | ISSUED, UNAVAILABLE, SUBSTITUTED. جيدة. |
| `ApprovalDecision` | PENDING, APPROVED, REJECTED. أضف `EXPIRED` (انتهت مهلة الطلب دون قرار). |

### 1.4 الطبيب والصيدلية والمختبر

| Enum | الملاحظة |
|---|---|
| `DoctorOrderStatus` | ACTIVE, MODIFIED, STOPPED. أضف `COMPLETED` (أمر نُفّذ كاملاً) و`EXPIRED` (انتهت مدته). |
| `PrescriptionStatus` | ACTIVE, DISPENSING, DISPENSED, MODIFIED, STOPPED. أضف `PARTIALLY_DISPENSED` و`REJECTED_BY_PHARMACY` (تعارض دوائي/عدم توفر) مع سبب يصل الطبيب كإشعار. |
| `LabOrderItemStatus` | ORDERED→SAMPLE_COLLECTED→PROCESSING→RESULT_ENTERED→FINAL/AMENDED/CANCELLED. أضف `SAMPLE_REJECTED` (عينة تالفة/غير كافية → إعادة سحب) و**علامة نتيجة حرجة** (`isCritical`) تُطلق تنبيهاً فورياً للطبيب. |
| `IncidentStatus` | OPEN, UNDER_REVIEW, CLOSED. أضف `ACTION_REQUIRED` و`ACTION_DONE` (الإجراء التصحيحي)، فالإغلاق بلا خطة تصحيح لا يفيد الجودة. |

### 1.5 حالات جديدة مطلوبة (غير موجودة)

1. **حالة الموظف:** `ACTIVE / SUSPENDED / ON_LEAVE / TERMINATED` بدل `isActive` فقط (انظر §3).
2. **حالة الإشعار:** `UNREAD / READ / ACTIONED` (انظر §4.3).
3. **حالة المهمة:** `OPEN / DONE / OVERDUE` لقائمة "عملي اليوم" لكل دور.
4. **حالة المستند/الموافقة:** موافقة المريض وإجراءات السلامة، إن اعتُمدت.

> **قاعدة معمارية للحالات:** كل enum فيه دورة حياة يحصل على (أ) جدول انتقالات مركزي، (ب) دالة انتقال واحدة، (ج) جدول تاريخ append-only. الأجهزة والصيانة والمختبر تطبّق (أ) و(ب) فعلاً؛ الجلسات والوصفات والحوادث تحتاجها.

## 2) جرد حالات الواجهة (Frontend state)

- 14 صفحة إدارية + الدخول + الإعدادات. حجم الصفحات: `doctor` 897 سطراً، `inventory` 660، `quality` 538، `maintenance` 448، `nursing` 418.
- توجد طبقة أساس جيدة بدأت: `useApi` (يمنع نتائج قديمة)، `useApiLoading` + `GlobalLoader`، `PaginatedTable`، `EmptyState`، `Skeleton`، `useLiveUpdates` (Socket.IO)، `i18n` عربي/إنكليزي.
- **المشاكل المتبقية:**
  - كل صفحة تدير `loading/error/form` يدوياً (`useState` متكرر، `<p className="text-red-600">` خام).
  - الصفحات الكبيرة تحوي عدة مكونات في ملف واحد، مما يصعّب الاختبار.

  - التوكن في كوكي غير `HttpOnly` (`document.cookie`) فهو مكشوف لأي XSS.
  - `useCurrentUser` يستدعي `/auth/me` في كل صفحة (لا سياق مشترك).

**د) الأمان الناقص:**

- `cors: true` مفتوح لأي Origin، وبوابة Socket.IO `origin: "*"`. قيّدهما بنطاق الواجهة.
- لا `helmet` ولا `ThrottlerModule` عام.

### 3.3 المطلوب في الواجهة (شاشات المدير)

صفحة جديدة `/admin/staff` (صلاحية `user.view`):
1. **قائمة الموظفين:** جدول مرقّم، بحث، فلتر (الدور/الحالة)، شارة حالة، آخر دخول.
2. **إضافة موظف (معالج 3 خطوات):** (1) البيانات الأساسية والمهنية، (2) اختيار الدور من قوالب مع **معاينة "ماذا سيرى هذا الموظف"** (قائمة الأقسام التي ستظهر له)، (3) كلمة مرور مؤقتة + طباعة/نسخ بطاقة الدخول.
3. **تفاصيل الموظف:** تبويبات (معلومات، الأدوار والصلاحيات، النشاط، الجلسات النشطة)، وأزرار: إعادة تعيين كلمة المرور، تعطيل/تفعيل، إنهاء الجلسات (رفع `tokenVersion`).
4. **مصفوفة الصلاحيات** `/admin/staff/roles`: أدوار في الأعمدة، صلاحيات مجمّعة بالـ module في الصفوف، مربعات اختيار، مع تحذير قبل الحفظ وعرض الفرق (Diff) عن الحالي. تمنع الحفظ إن أفقد النظام آخر مدير.
5. **سجل التدقيق** `/admin/audit` (الـ API موجود `audit.view` ولا توجد واجهة له).

## 4) واجهة لكل موظف (Role-based Workspaces)

### 4.1 المبدأ
ما يفعله الموظف **هو صفحته الرئيسية**. بعد الدخول يُوجَّه إلى مساحة عمله، ولا يرى ما لا يخصه.

### 4.2 الصفحة الرئيسية لكل دور

| الدور | الوجهة بعد الدخول | ما يُعرض في الأعلى |
|---|---|---|
| المدير / مدير المركز | `/admin` (لوحة المركز) | إشغال اللحظة، أجهزة معطلة، تنبيهات مخزون، حوادث مفتوحة، مؤشرات اليوم |
| الطبيب | `/admin/doctor` | مرضاي اليوم، جلسات جارية بها تنبيه، **نتائج مختبر حرجة تنتظر قراري**، وصفات تنتظر تعديلاً |
| الممرض | `/admin/nursing` | ردهتي: كل سرير + حالة الجلسة + الخطوة التالية (مثلاً "بحاجة قراءة ضغط منذ 25 د") |
| الصيدلي | `/admin/pharmacy` | طابور الصرف مرتباً بالأولوية، أدوية قاربت النفاد |
| المختبر | `/admin/lab` | طابور العينات (سحب/معالجة/إدخال نتيجة) مع مؤقّت الانتظار |
| الاستقبال | `/admin/reception` | وصول اليوم، المتأخرون، الغائبون، حجز موعد إضافي |
| المخزن | `/admin/inventory` | طلبات التحويل المعلّقة، دفعات قاربت الانتهاء |
| الصيانة | `/admin/maintenance` | بلاغات مفتوحة حسب الخطورة وتجاوز SLA |

**التنفيذ:** حقل `landingPath` لكل دور في `role-templates.ts` يعيده `/auth/me`، ويستخدمه `login` للتوجيه. الأقل تكلفة: بلا جداول جديدة.

### 4.3 مكونات مشتركة لكل الأدوار
1. **مركز الإشعارات (جرس):** جدول `Notification` + `GET /notifications` + دفع عبر Socket.IO (الـ gateway موجود). أمثلة: نتيجة حرجة للطبيب، وصفة جديدة للصيدلي، جلسة وصلت للممرض، جهاز تعطل للمدير.
2. **"عملي الآن" (Work Queue):** endpoint موحّد `GET /me/work-queue` يجمع المهام المعلّقة حسب صلاحيات المستخدم (الجزء الموجود في `dashboard/pending-work` يخدم المختبر والصيدلية فقط؛ عمّمه).
3. **بحث سريع عن المريض** (موجود في الشل) مع اختصار لوحة مفاتيح `Ctrl+K`.
4. **تسليم الوردية (Handover):** ملاحظات نهاية الوردية لكل ردهة، مع حالة "استُلمت".
5. **حالات فارغة وأخطاء واضحة:** استخدام `EmptyState`/`Skeleton` (موجودان) بدل الرسائل الخام.

### 4.4 ملاحظات لكل دور (نقاط الألم المتوقعة)

- **الطبيب (897 سطراً في صفحة واحدة):** تقسيم إلى تبويبات مسارات (أوامر، وصفات، ملاحظات، مختبر)، وشريط مريض ثابت (اسم، عمر، وزن جاف، حساسية، وصول وعائي، تنبيهات حرجة) يبقى ظاهراً عند التمرير.
- **الممرض:** أزرار كبيرة ولمس مناسب لجهاز لوحي بجانب السرير؛ إدخال قراءات سريع بأرقام؛ تنبيه بصري إذا خرجت القراءة عن الحدود (ضغط منخفض…).
- **المختبر:** إدخال نتائج دفعي (Grid) مع مدى مرجعي وعلامة H/L/Critical تلقائية.
- **الصيدلي:** تنبيه تعارض دوائي وحساسية قبل الصرف، وطباعة ملصق.
- **الاستقبال:** شاشة واحدة: بحث → تسجيل وصول → تعيين سرير، بأقل نقرات.
- **الإدارة:** لوحة تنفيذية بمؤشرات (زمن الانتظار، نسبة الغياب، إشغال الأجهزة، مضاعفات لكل 100 جلسة) وقابلة للتصدير.

## 5) تحسينات الواجهة التقنية

1. **سياق مستخدم واحد** (`<AuthProvider>`): `/auth/me` مرة واحدة، ويوفّر `can(permission)`.
2. **مكوّن `<Can permission="x">` وحارس مسار:** إن دخل المستخدم رابطاً لا يملك صلاحيته تظهر صفحة "غير مصرّح" واضحة بدل صفحة فارغة/خطأ.
3. **نقل التوكن إلى كوكي `HttpOnly`** يضعه الـ API عند الدخول (وإضافة Refresh Token قصير العمر)، بدلاً من `document.cookie`.
4. **توحيد النماذج:** مكوّن `<FormField>` + معالج أخطاء API واحد يُظهر أخطاء التحقق تحت كل حقل (الـ API يعيد `message[]` من class-validator).
5. **ترحيل الصفحات القديمة إلى HeroUI** تدريجياً، الأولوية للأكثر استخداماً: doctor → nursing → reception → lab → pharmacy.
6. **تقسيم الصفحات الكبيرة** إلى مكونات (`doctor/OrdersTab.tsx`…) لتسهيل الصيانة والاختبار.
7. **إمكانية الوصول:** الأساسيات موجودة (skip-link، RTL). أضف تباين ألوان الحالات، ولا تعتمد على اللون وحده للحالة (أيقونة + نص).
8. **وضع الشاشة الكبيرة (Wall Display)** لشاشة الردهة: عرض حالة الأسرّة فقط بلا تفاعل، تُحدَّث عبر Socket.IO.
9. **اختبارات:** يوجد Playwright (6 اختبارات على خادم وهمي). أضف اختباراً لكل دور: يدخل، يصل لصفحته، ولا يرى غيرها.

## 6) تحسينات الـ API لتكون مستدامة وقابلة للتطوير

### 6.1 ترقيم وفلترة موحّدة
- اليوم فقط `GET /patients` يعيد `{data,total}`. **المطلوب:** غلاف موحّد لكل قائمة: `{ data, meta: { page, limit, total, totalPages } }` مع `PaginationQueryDto` مشترك، وفرز (`sort=field:asc`) وبحث (`q=`).
- الأولوية: `users`, `audit`, `schedule`, `lab-orders`, `prescriptions`, `stock movements`, `incidents`, `maintenance tickets`.

### 6.2 ثراء الاستجابات (ما تُرجعه الـ endpoints)
- **قوائم خفيفة وتفاصيل غنية:** القائمة تعيد حقول العرض فقط، والتفاصيل تعيد كل شيء. تجنّب N+1 في الواجهة (مثلاً جلب المريض لكل جلسة).
- إضافة **حقول محسوبة** في الاستجابة بدل حسابها بالواجهة: `allowedActions: ["start","interrupt"]` لكل جلسة/أمر (تُحسب من الحالة والصلاحيات)، وهذا يُلغي تكرار منطق "أي زر يظهر" في الواجهة.
- إضافة `nextStep` و`waitingMinutes` و`isOverdue` للجلسات والطلبات.
- أخطاء موحّدة: `{ statusCode, code: "MACHINE_NOT_AVAILABLE", message, details }` برمز نصي ثابت تترجمه الواجهة (عربي/إنكليزي) بدل نص إنكليزي حرّ.

### 6.3 الصلاحيات كعقد
- `GET /auth/me` يعيد أيضاً: `landingPath`, `navigation` (الأقسام المتاحة)، `mustChangePassword`. تصبح الواجهة مرآة للخادم فلا يتكرر جدول الصلاحيات في `AdminShell`.
- تحويل مفاتيح الصلاحيات إلى ثوابت مصدّرة من `@dcms/shared` (تُستخدم في الـ API والواجهة) بدل نصوص حرة.

### 6.4 الأحداث والتزامن
- الـ Gateway يبث `entity` فقط. وسّعه إلى `{ entity, id, action }` وغرف لكل ردهة/دور (`ward:{id}`, `role:{name}`) لتحديث جزئي بدل إعادة جلب كل شيء.
- اعتماد **EventEmitter → جدول Outbox** قبل أي نشر مستقبلي (إشعارات، تكامل خارجي) كي لا تضيع الأحداث عند الانقطاع.

### 6.5 قابلية التشغيل والتوسع
- `ThrottlerModule` عام + `helmet` + تقييد CORS.
- **محدد المحاولات** (`login-rate-limiter`) إلى Redis أو جدول DB، كي يعمل مع أكثر من نسخة.
- فهارس قاعدة البيانات لاستعلامات الجداول الكبيرة: `DialysisSchedule(date, shiftId)`, `AuditLog(createdAt)` (موجود جزئياً)، `LabOrderItem(status)`.
- **أرشفة**: `AuditLog` و`DialysisReading` ستكبر بسرعة (1000 مريض × 3 جلسات/أسبوع × قراءات متعددة). خطّط للتقسيم (Partitioning) أو الأرشفة السنوية.
- نسخ احتياطي واستعادة مُختبرة، وفصل بيئات (dev/staging/prod)، وCI يشغّل الـ Lint والبناء وسكربتات الاختبار الموجودة (`scripts/test-*.cjs`).
- **الإصدارات:** المسار `/api/v1` موجود. اعتمد قاعدة "لا كسر داخل v1؛ الحقول تُضاف فقط"، وحدّث `openapi.yaml` آلياً ضمن CI.
- التوثيق: ولّد عميلاً مكتوباً (typed client) من `openapi.yaml` للواجهة بدل `types.ts` اليدوي (719 سطراً) الذي قد ينحرف عن الخادم.

### 6.6 الاختبارات
الاختبارات الحالية سكربتات `.cjs` تُنفَّذ يدوياً. أضف Jest/Vitest لوحدات منطق الحالات (جداول الانتقال) واختبارات e2e لمسار: تسجيل مريض → جدولة → وصول → جلسة → صرف → مختبر.

## 8) أسئلة للنقاش

1. **الأدوار:** هل الـ 12 دوراً كافية لمركزكم؟ هل تريدون أدواراً مخصصة يُنشئها المدير (مثلاً "ممرض عناية مركزة")؟
2. **قوالب الصلاحيات في §3.2:** هل هي مطابقة لعملكم؟ أخصّ بالسؤال: هل يرى الاستقبال الملف الطبي أم بيانات الهوية والجدولة فقط؟
3. **النطاق:** هل يرى الممرض مرضى ردهته/ورديته فقط، أم كل المرضى؟ وهل يرى الطبيب مرضاه فقط أم الكل؟
4. **الدخول:** هل تريدون بطاقة/بصمة/PIN سريع على أجهزة الردهة المشتركة؟ (الـ PIN موجود للتمريض).
5. **اللغة:** عربي فقط للموظفين أم ثنائية اللغة؟ (مدعومة حالياً).
6. **الاستضافة:** داخل المركز (On-Premise) أم سحابة؟ يؤثر على النسخ الاحتياطي والأداء والامتثال لخصوصية البيانات الطبية.
7. **الأجهزة اللوحية:** هل سيُستخدم النظام على أجهزة لمس بجانب السرير؟ إن نعم نرفع أولوية تصميم اللمس.
8. **الأولوية:** نبدأ بـ A (الموظفون والصلاحيات) كما أقترح، أم بشيء آخر؟

## 9) قرارات النقاش وتعديل الخطة (الإصدار 2)

### 9.1 القرارات
1. **لا تقييد بالردهة.** أي موظف يرى المرضى حسب صلاحية دوره فقط (لا نطاق ردهة/طبيب). يُحذف بند "النطاق" من §3.2-د.
2. **بدل التقييد: المساءلة الكاملة.** كل موظف يُسجَّل نشاطه، ويستطيع كتابة إجراء أو تقرير. السجل قابل للتفتيش من لجان دائرة الصحة.
3. **البداية من الـ API الإداري** (الموظفون، الأدوار، التوجيه حسب الدور، سجل النشاط، التقارير). الواجهة تُبنى فوقه بعد ذلك.

### 9.2 سجل النشاط والتفتيش (Audit/Activity)

**الموجود:** `AuditLog` append-only (الفاعل، الدور، الإجراء، القيمة قبل/بعد، السبب، الجهاز، IP). لكنه يُكتب يدوياً داخل كل خدمة، ويسجّل **الكتابة فقط**.

**الناقص للتفتيش الرسمي:**

| الفجوة | الحل |
|---|---|
| لا تُسجَّل **قراءة** ملف المريض | Interceptor عام يسجّل `PATIENT_VIEWED` / `REPORT_EXPORTED` عند فتح ملف مريض أو تصدير (من، متى، أي مريض) |
| لا ربط بالوردية | إضافة `shiftId` و`sessionId` و`patientId` اختيارية إلى `AuditLog` وفهارس عليها، لسؤال "ماذا حدث لهذا المريض في هذه الوردية" |
| لا دليل على عدم التلاعب | سلسلة تجزئة: حقل `prevHash` + `hash` لكل سجل، مع endpoint `GET /audit/verify` يكشف أي تعديل في القاعدة خارج النظام |
| لا سجل يومي لكل موظف | `GET /me/activity?date=` و`GET /users/:id/activity?from=&to=` (مرقّم، مجمّع باليوم) |
| لا تصدير للجهات الرقابية | `GET /audit/export?from&to&actor&patient&format=csv\|pdf` بختم زمني ومن أصدره (ويُسجَّل التصدير نفسه) |
| لا دور مفتّش | دور **`AUDITOR`** للقراءة فقط (`audit.view` + `report.view` + `incident.view`) بحساب مؤقت له تاريخ انتهاء، لا يرى كلمات مرور ولا يعدّل شيئاً |
| الاحتفاظ | سياسة احتفاظ (مثلاً 10 سنوات) وأرشفة بلا حذف؛ لا مسار حذف/تعديل للسجل (قائم أصلاً) |

### 9.3 إجراءات وتقارير الموظف (نموذج واحد)

نموذج واحد **`StaffEntry`** يغطي: إجراء يدوي، تقرير الدوام، مشكلة، شكوى، مقترح. (لا نماذج منفصلة؛ يختلف `type` فقط.)

| الحقل | الوصف |
|---|---|
| `type` | `ACTION_NOTE` / `SHIFT_REPORT` / `PROBLEM` / `COMPLAINT` / `SUGGESTION` |
| `authorId`, `shiftId`, `entryDate` | الكاتب والوردية واليوم |
| `title`, `body`, `category` | النص والتصنيف (جهاز، مريض، زميل، مخزون، بيئة…) |
| `severity` | LOW/MEDIUM/HIGH/CRITICAL |
| `patientId?`, `sessionId?`, `machineId?` | ربط اختياري بالسياق |
| `complaintSource?` | `STAFF` / `PATIENT` / `FAMILY` (للشكاوى) |
| `isConfidential` | الشكوى على زميل/إدارة تُخفى عن غير المراجعين |
| `status` | `SUBMITTED → ACKNOWLEDGED → IN_PROGRESS → RESOLVED → CLOSED` (+ `REJECTED`) |
| `assignedToId`, `response` | من يعالجها وردّ الإدارة (يصل الكاتب) |
| `escalatedIncidentId?` | تحويلها إلى `IncidentReport` عند كونها حادثة سلامة |

+ جدول `StaffEntryStatusHistory` (append-only، نفس نمط الحوادث/الصيانة) وجدول تعليقات بسيط.

**تقرير الوردية:** `GET /me/shift-summary?shiftId=` يعيد ملخصاً تلقائياً (عدد الجلسات، القراءات، الأحداث، الحوادث، الأجهزة المتأثرة، إجراءات الموظف) ليضيف الموظف تعليقه ويقدّمه بضغطة. يمنع "نسيان" التقارير.

**الـ API:**

| المسار | الصلاحية |
|---|---|
| `POST /staff-entries` | `entry.create` (كل موظف) |
| `GET /staff-entries/mine` | كل موظف (يرى ما كتبه وحالته وردّ الإدارة) |
| `GET /staff-entries?type&status&author&from&to&page` | `entry.review` |
| `PATCH /staff-entries/:id/status` / `POST …/assign` / `POST …/respond` | `entry.review` |
| `POST /staff-entries/:id/escalate` | `entry.review` + `incident.report` |
| `GET /me/shift-summary` | كل موظف |

### 9.4 التوجيه حسب الموظف

- `GET /auth/me` يعيد: `landingPath`، `navigation[]` (الأقسام المسموحة مرتبة)، `mustChangePassword`، `roles`، `permissions`.
- `landingPath` يُعرَّف في `role-templates.ts` (§3.2-أ) ويُقرأ عند الدخول. الواجهة تتبع الخادم بلا جدول موازٍ.
- الأدوار المخصصة (تُنشأ من الواجهة) تختار `landingPath` من قائمة.
- صلاحيات جديدة: `entry.create`, `entry.review`, `report.view`, `audit.export`, `user.update`, `user.reset_password`, `role.create`.

### 9.5 سجلات المرضى وتحديثات الـ API

من خطة V1 القائمة، والمقترح تقديمه لأنه يخدم الـ API الإداري والتفتيش:

1. `GET /patients/:id/overview`: استدعاء واحد بدل عدة (بيانات أساسية، وزن جاف، وصول وعائي، تنبيهات مفتوحة، آخر جلسة، آخر مختبر، أدوية فعالة، مواعيد قادمة).
2. `GET /patients/:id/timeline?page&type&from&to`: مرقّم وقابل للفلترة (الموجود غير مرقّم). كل حدث يحمل `actor` و`shift`.
3. **تاريخ التغييرات في بيانات المريض:** `GET /patients/:id/history` (قبل/بعد لكل تعديل من `AuditLog`) ليعرف المفتّش من غيّر ماذا.
4. `statusReason` و`statusChangedAt` وحالتا `ON_HOLD` و`TRANSPLANTED` (§1.1).
5. `AccessRecord` سجل الوصول الوعائي كنموذج مستقل (V1 §4.3).
6. حالة التنبيه (`OPEN/ACKNOWLEDGED/RESOLVED`) مع من أقرّ به.
7. **موافقة/إفصاح:** تسجيل من اطّلع على ملف VIP أو حساس ("Break-the-glass": يطلب سبباً قبل الفتح ويُسجَّل).
8. باقي V1 (المسار السريري، التحاليل الدورية، الأدوية، الإجراءات) تبقى في خطتها.

## 11) الإصدار الثالث: القرارات والتنفيذ الكامل (21 أيلول 2026)

### 11.1 قرارات صاحب القرار
1. **حساب اللجان ودائرة الصحة:** لوحة رقابة فقط، مخططات تفاعلية لكل أقسام المركز + السجلات على خط زمني. لا أقسام، لا نماذج، لا أسماء مرضى (رمز المريض فقط).
2. **شكاوى المرضى** تُحفظ، وكل شكوى **تُرفع تلقائياً لمدير المركز** مع إشعار.
3. **إلزام تقرير الدوام** خيار في الإعدادات لمدير النظام (SUPER_ADMIN) فقط.
4. **إكمال كل التقنيات المؤجلة.**

### 11.4 ما لم يُنفَّذ (بصراحة)
- **ترحيل صفحات الطبيب/المخزون/الجودة/الصيانة/التمريض القديمة إلى HeroUI وتقسيمها إلى مكونات:** لم يُنفَّذ (صفحات ضخمة تحتاج مراجعة سريرية وظيفة بوظيفة)؛ الصفحات الجديدة تتبع نمط الصفحات الحالية.
- **حالات لم تُضف لأنها بلا مسار عمل واضح بعد:** `MaintenanceTicket.CANCELLED` (تتداخل مع إعادة الجهاز للخدمة)، `Approval.EXPIRED` (يحتاج مجدولاً)، `PARTIALLY_DISPENSED`، `DoctorOrder.COMPLETED/EXPIRED`، `Schedule.RESCHEDULED`، حالات الجلسة `CANCELLED_BEFORE_START/TRANSFERRED_OUT`.
- **نطاق الحد الأعلى للمعدل** لكل نسخة (ذاكرة)؛ عند تعدد النسخ يوضع محدد مشترك على الـ reverse proxy.
- الإشعارات المرسلة داخل معاملة قد تصل حتى لو فشلت المعاملة لاحقاً (نادر جداً).
