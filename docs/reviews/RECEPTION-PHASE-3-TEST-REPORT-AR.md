# نتيجة اختبار الفيز 3 — Reception

تاريخ الاختبار: 2026-09-08.

**النتيجة: الفيز لا يجتاز القبول كاملاً بعد.** نجح 18 من 25 اختباراً آلياً، وفشل 7. بناء API والويب نجح، والمهاجرات الخمس طبقت بنجاح على PostgreSQL 16 مؤقتة ومعزولة. لا تمثل هذه النسبة قياساً لتغطية الكود أو اختبار حمل.

## بيئة الاختبار والأدلة

- قاعدة `reception_test` داخل حاوية مستقلة، بمنفذ عشوائي على localhost؛ بيانات مرضى ومستخدمين اصطناعية فقط.
- شغلت AppModule الفعلية داخل Nest على منفذ مؤقت مع ValidationPipe وJWT وPermissionsGuard الحقيقيين. معظم السيناريوهات عبر HTTP، مع فحص ما حُفظ فعلياً باستخدام Prisma.
- ثبتُّ ساعة عملية الاختبار على 2026-09-08 وغيرتها لكل حالة مع `TZ=Asia/Baghdad`. لم يتغير وقت الجهاز أو قاعدة المشروع.
- اختبار التزامن يستخدم الخدمة الفعلية وكتابات PostgreSQL فعلية، مع حاجز اختباري يؤخر اكتمال القراءتين حتى ترى كلتاهما SCHEDULED؛ هذا ترتيب متزامن ممكن، وليس قياساً لتكرار المشكلة تحت حمل عشوائي.
- اختبار rollback يحقن فشل خدمة التدقيق فقط ثم يتحقق من التراجع الحقيقي داخل PostgreSQL.
- [النتائج الآلية التفصيلية](RECEPTION-TEST-RESULTS.json)، و[سكربت إعادة الاختبار](../apps/api/scripts/test-reception-review.cjs).
- تعذر تشغيل اختبار المتصفح بسبب خطأ أداة الاتصال `missing field sandboxPolicy`. لم يتم اختبار تفاعل الواجهة أو جهاز مسح باركود فعلي؛ نتائج الواجهة أدناه من مراجعة الكود والبناء، وليست قبولاً بصرياً.
- لم تتغير الشيفرة التشغيلية أو بيانات المشروع. أزيلت حاوية الاختبار بعد الانتهاء.

## معايير القبول السبعة

| المعيار | النتيجة | الدليل والحدود |
|---|---|---|
| الباركود يعرض الهوية والإضبارة وجلسة اليوم | جزئي | HTTP أعاد الاسم والإضبارة والجلسة الصحيحة. صورة المريض المذكورة بالخطة غير موجودة في النموذج/الشاشة. لم يختبر قارئ مادي. |
| حفظ ARRIVED مع الوقت والموظف والمحطة | جزئي | نجح الحفظ مع القيم الصحيحة وAudit/Timeline عند إرسال محطة. يقبل غياب المحطة، ويقبل تكراراً متزامناً. |
| LATE وحساب التأخير وTimeline | جزئي | 06:31 لوجبة 06:00 وحد 30 يعطي LATE. 06:30:01 يعطي ARRIVED بسبب التقريب قبل المقارنة. |
| ABSENT تلقائياً مع حفظ الموعد | جزئي | قراءة الجدول بعد 10:00 حولت الموعد إلى ABSENT وحفظت absentMarkedAt دون حذف. لم تُكتب أحداث التدقيق/التاريخ. يعمل عند القراءة فقط. |
| باركود غير موجود بخطأ واضح | ناجح في API | 404، وليس 500. توجد معالجة خطأ بالواجهة في الكود، دون اختبار تفاعل متصفح. |
| لوحة الحالات وتحديثها | تحقق API وفحص كود؛ المتصفح غير مختبر | الجدول يعكس انتقالات الحالات؛ الكود يعرض العدادات ويطلب تحديثاً كل 15 ثانية عند عرض اليوم. لم يقس تأخير التحديث داخل متصفح. |
| تقرير الغياب يعرض المريض | ناجح في API فقط | `/schedule?date=2026-09-08&status=ABSENT` أعاد المريض المتغيب. لا شاشة مخصصة لتصفية الغياب أو تصديره في الواجهة الحالية. |

## الاختبارات السبعة الفاشلة

| الحالة | المتوقع | الفعلي | المرجع |
|---|---|---|---|
| الحضور عند 06:30:01 وحد التأخير 30 دقيقة | LATE إذا كانت القاعدة تجاوز الحد بالوقت الفعلي | ARRIVED | DCMS-039 |
| حضور موعد 9 أيلول أثناء يوم 8 | رفض خارج نافذة الحضور | 201 ARRIVED | DCMS-037 |
| حضور موعد 7 أيلول أثناء يوم 8 | مسار تصحيح صريح، لا حضور عادي | 201 LATE | DCMS-037 |
| Check-in دون stationId | رفض أو تعيين محطة موثوقة تلقائياً | 201 ومحطة غير مسجلة | DCMS-040 |
| التحويل التلقائي إلى ABSENT | Audit وTimeline | صفر Audit وصفر Timeline | DCMS-038 |
| status=NOT_A_STATUS | 400 | 500 | DCMS-041 |
| طلبا حضور متزامنان لنفس الموعد | كتابة حضور واحدة | نجاحان وسجلا Audit؛ آخر كتابة تستبدل بيانات الأولى | إعادة إنتاج متخصصة لـDCMS-004 |

نافذة الحضور والتقريب يحتاجان سياسة تشغيل مكتوبة. اختبارات اليوم السابق/التالي تفترض أن endpoint الحضور العادي لا يستخدم لتصحيح التاريخ أو تسجيل الوصول قبل الموعد بيوم؛ إذا كانت هناك استثناءات، تنفذ بنطاق زمني وصلاحية وسبب واضحين، وليس سماحاً غير محدود.

## ما نجح فعلياً

الحراسة أعادت 401 دون JWT و403 لحساب بلا صلاحية في scan وcheck-in. الباركود الصحيح أعاد الجلسة الصحيحة؛ الباركود ومعرف الموعد غير الموجودين أعادا 404. رفض السيرفر إدخال checkInTime من العميل بـ400. الحضور الطبيعي سجل المستخدم والمحطة والوقت والتأخير وAudit وTimeline. التكرار المتعاقب رفض بـ409 دون سجل تدقيق إضافي. حد 30 دقيقة بالضبط أعاد ARRIVED، وبعد 31 دقيقة أعاد LATE. الجلسات EXTRA وEMERGENCY قبلت الحضور وحافظت على type، بينما CANCELLED رفضت بـ409. قراءة الجدول علمت الغياب، وتكرار القراءة لم يغير absentMarkedAt. حضور المريض بعد تعليمه غائباً أعاد LATE مع Timeline. فشل Audit المحقون ألغى الحضور بالكامل.

## ملاحظات لا تُحسب ضمن الاختبارات الآلية

- `ensureAbsencesMarked` يعمل عند قراءة اليوم فقط. الخطة تسمح بالفحص عند القراءة، لكن MODULES-SPEC يشترط Job؛ يلزم توحيد المرجعين. إذا أغلقت الشاشات لا يوجد عامل خلفي في هذه الوحدة يعلّم الغياب، وقراءة يوم جديد لا تعالج اليوم السابق. هذه امتداد لفجوة دورة الجدولة DCMS-034، وليست مشكلة جديدة مكررة.
- نافذة الغياب مربوطة بنهاية الغسيل `dialysisEnd`، وليست إعداداً مستقلاً لنافذة الحضور. تأكد أن هذا يطابق سياسة المركز قبل القبول.
- جميع أجهزة الواجهة ترسل `RECEPTION-1`؛ لا يثبت ذلك هوية المحطة الفعلية.
- صورة المريض المطلوبة بمعيار القبول غير مدعومة حالياً؛ راجع DCMS-042.
- لم يجر اختبار ضغط، أو نشر صور Docker للتطبيق، أو حساب runtime المقيد/harden-db.sql. حساب اختبار قاعدة البيانات هو حساب مالك القاعدة المؤقتة. نجاح المعاملات هنا لا يصادق على grants في نشر الإنتاج.
- لم أكرر مراجعة أو أغلق بنود المرحلتين السابقتين؛ الفحص مركز على الاستقبال.

## إعادة الاختبار

من PowerShell في جذر المستودع، استخدم حاوية مؤقتة جديدة. المثال يثبت منفذ اختبار محلي؛ اختر منفذاً شاغراً إذا كان مشغولاً. لا تستعمل قاعدة التطبيق.

```powershell
docker run --rm -d --name dcms-reception-review-test -e POSTGRES_PASSWORD=reception-test-only -e POSTGRES_DB=reception_test -p 127.0.0.1:25433:5432 postgres:16-alpine
docker exec dcms-reception-review-test pg_isready -U postgres -d reception_test
# انتظر جاهزية PostgreSQL قبل المتابعة.
$env:DATABASE_URL = 'postgresql://postgres:reception-test-only@127.0.0.1:25433/reception_test?schema=public'
$env:TEST_DATABASE_URL = $env:DATABASE_URL
try {
  npm run prisma:deploy --workspace=@dcms/api
  if ($LASTEXITCODE -ne 0) { throw 'Test migrations failed' }
  npm run build:api
  if ($LASTEXITCODE -ne 0) { throw 'API build failed' }
  node apps/api/scripts/test-reception-review.cjs
} finally {
  docker stop dcms-reception-review-test
  Remove-Item Env:DATABASE_URL
  Remove-Item Env:TEST_DATABASE_URL
}
```

السكربت يرفض عنوان اختبار لا يشير إلى localhost وقاعدة باسم reception_test، ويضيف بيانات اصطناعية دون تنظيف قاعدة موجودة. شغله على حاوية جديدة لكل جولة. يكتب نتائج JSON ويخرج برمز 1 عند فشل معيار، أو 2 عند خطأ إعداد/تنفيذ. بناء الويب يفحص منفصلاً عبر `npm run build:web`. عنوان القاعدة الصريح يتقدم على قيمة DATABASE_URL في ملفات البيئة عند تشغيل Prisma CLI.

## قرار القبول

أصلح تعارض الحضور المتزامن ونافذة الحضور والتدقيق التلقائي والمحطة، وثبت سياسة حد التأخير، ثم أعد نفس الاختبارات. أكمل اختبار المتصفح والعدادات بعد إصلاح اتصال أداة المتصفح، وقرر متطلب الصورة وواجهة تقرير الغياب مع صاحب المشروع. لا أوصي باعتبار الفيز 3 مقبولاً كاملاً قبل ذلك.
